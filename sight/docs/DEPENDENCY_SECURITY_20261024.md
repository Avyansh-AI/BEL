## Finding and bounded plan

The audit queried the public OSV API using only the 38 installed Python package names and versions. It returned **41 advisory records**: two aliases for the Certifi issue and 39 Pillow records. These are package-version findings, not 41 demonstrated SIGHT exploits. The [original scan](../../audit-tests/20261023-local-model/dependencies/reports/dependency_audit.json) is retained. No API keys, user prompts or owner data were sent.

Certifi 2026.7.22 trusted an emSign root associated with compromised intermediate keys. The maintainer's [security advisory](https://github.com/certifi/python-certifi/security/advisories/GHSA-6q48-6c7w-9gw2) describes the trust-store removal. OSV identifies 2026.10.19 as the fixed release restoring unaffected roots. This matters to SIGHT's HTTPX TLS clients when cloud providers are explicitly enabled; the local-only configuration does not justify leaving an affected trust bundle pinned.

Pillow 12.3.0 has multiple upstream parser/native-memory findings addressed in [Pillow 13.0.0](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html). This checkout imports Pillow in visual regression tests, not its live backend. The audit nevertheless repairs the installed and pinned development dependency. One concrete regression uses the malformed XBM pattern described by the [maintainer's advisory](https://github.com/python-pillow/Pillow/security/advisories/GHSA-xgh8-jp6q-p5x8), with a five-second child-process deadline to bound the reproduction.

Further inspection found a separate affected trust bundle vendored inside pip 26.2. Updating top-level Certifi did not replace that copy. A third behavior test reproduced the affected root in pip's own SSL trust store. [pip 26.2.2 release notes](https://pip.pypa.io/en/stable/news/) identify its updated Certifi 2026.10.19 bundle. Both bootstrap and installed pip pins were updated to 26.2.2 using verified official distribution hashes. This finding illustrates a limit of the top-level package advisory scan.

Plan: reproduce affected behavior, verify fixed distributions and dependency metadata from PyPI, change only the three necessary pins, install from hash-verified local wheels, rerun regressions/advisory scans, then rerun the full suite, real Gemma/application acceptance and a separate 3,600-second soak. No new runtime package, model weight change or provider activation is needed. The later live model-quality failure is investigated separately below.

## Limits and release decision

The 24 October OSV scan's zero matches is a scoped advisory result, not proof that dependencies or external binaries are vulnerability-free or that no later advisory exists. The scan does not clear every bundled component in Ollama, Chromium, pip, Windows or the GPU driver. No credential compromise is asserted. The published ZIP and earlier phase environments were not modified by this local update.

A separate upstream-version review confirmed that the installed Playwright 1.64.0 uses Chromium/Headless Shell 156.0.8078.4 (revision 1248). The [Playwright 1.64.1 browser manifest](https://raw.githubusercontent.com/microsoft/playwright/v1.64.1/packages/playwright-core/browsers.json) still specifies that same browser; its [release notes](https://github.com/microsoft/playwright/releases/tag/v1.64.1) describe Electron-window and cross-origin routing fixes, not a demonstrated fix for this screenshot failure. Google's [20 October stable release](https://chromereleases.googleblog.com/2026/10/stable-channel-update-for-desktop_02018666648.html) is later at 156.0.8078.47/.48 and includes security fixes. This chronology warrants a separate browser patch/reachability review; it does not establish which fixes affect this isolated supplied-HTML path. No browser/runtime dependency was changed during the soak, and external-component security remains unqualified.

The first completed official-model soak passed all 468 checks, including backup/restore and three intentional backend crash/restarts, but used older dependencies and disabled thinking. It is preserved separately. The replacement run above independently qualifies the updated source/dependency/profile combination for its bounded workload; neither the 5.5-second failed start nor any earlier uncensored-model test contributed to its duration.

Next, investigate resource pressure and the intermittent screenshot failure with failure-time diagnostics, then qualify installation on a fresh Windows account. Passing the soak does not resolve those limitations or clear external-component security. Broader roadmap limitations remain explicit: executable Forge has no qualified isolation runtime here (Docker/Podman unavailable; WSL reports not installed), local microphone/STT/playback and personal wake enrollment are unimplemented and lack consent/recordings, and remote browser/desktop interaction and automated code repair require separate bounded implementation and tests. Existing memories, earlier phase data/configurations and the original UI were preserved; the current checkout's model setting was created with the owner's explicit thinking-profile approval. No paid services were enabled, no quota ledger reset, and no GitHub push or release performed. Overall readiness remains **PARTIAL**.
