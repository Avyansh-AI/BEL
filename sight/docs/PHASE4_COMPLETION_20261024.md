## Resource and stability findings

The successful lower-temperature thinking benchmark has a median reply time of **3.398 seconds** on this machine. The separate qualifying soak recorded **12/12 correct model answers**, with median latency **10.086 seconds** and maximum **44.844 seconds**. These are different bounded serial workloads; neither establishes general reasoning correctness, concurrent capacity or whole-day performance.

The qualifying soak ran for **3,601.906 seconds on 24 October**, with 60 cycles, all 468 checks passed, three deliberate backend crash/restarts and zero unplanned backend exits. It verified durable WebSocket requests, no stuck tasks, one receipt per completed task, interrupted-model review behavior and full data backup/restore. All **60 generated output files** survived restoration; the [backup manifest](../../audit-tests/20261024-security/current-build/soak-20261024T141055Z-6bba57/backup/manifest.json) also records both databases and the synthetic local-model selection. This used isolated test data, not an overwrite of the owner's data.

Across **706 telemetry samples**, GPU memory peaked at **4,405 MiB**, GPU temperature at **70°C**, host CPU at **87.81%**, and backend working set at **72.11 MiB**. Available host RAM reached a minimum of **67.33 MiB**. CPU temperature was unavailable through the interfaces used. GPU/host totals include other applications and must not be attributed wholly to SIGHT. The low RAM margin remains a capacity concern despite the successful bounded run; it does not justify adding concurrent models, speech or browser workloads without measurement. [Raw telemetry](../../audit-tests/20261024-security/current-build/soak-20261024T141055Z-6bba57/telemetry.jsonl).

The [26 October review](../../audit-tests/20261024-security/current-build/post-soak-review.json) confirmed that the recorded source hashes and dependency versions still match the checkout, with the same selected model and thinking setting. Maximum recorded health-check and telemetry gaps were **60.937 seconds** and **5.365 seconds** respectively. The review confirms the completed 24 October run; it does not extend its duration across the subsequent chat gap.

During the fresh-install browser rechecks, host memory use was approximately **95%**, with **680–695 MiB** available RAM and **865–879 MiB** available commit. Those measurements followed the screenshot failure; no failure-time telemetry exists. Memory pressure is a possible contributor, not an established cause. The tests did not disable browser sandboxing, change timeouts or terminate unrelated applications to obtain successful reruns.

The previous official-model soak completed **3,602.953 seconds**, **60 cycles** and **468/468 checks**, including three intentional backend crash/restarts and full data backup/restore. It used the older dependencies and disabled thinking, so it does **not** qualify this updated build. Its telemetry recorded host available RAM as low as **156.12 MiB** and GPU memory as high as **7,518 MiB**; these are shared-machine measurements, not SIGHT-only allocations. See the [historical official-model audit](LOCAL_MODEL_AUDIT_20261023.md). The earlier uncensored-model soak is also excluded from current acceptance.

## Release blockers and next development steps

1. Investigate and reduce host resource pressure before expanding concurrent workloads. Capture failure-time memory/commit and browser diagnostics to resolve or bound the intermittent Chromium screenshot failure. The successful soak and unchanged browser rechecks do not establish its root cause.
2. Qualify installation and startup on a fresh Windows account after the browser/resource investigation. Keep the passed current-build soak and its failed initial start as separate evidence; repeat qualification when a material runtime change requires it.
3. Maintain the reviewed local model/profile and evaluate additional task families without weakening error reporting or treating a small benchmark as general intelligence certification. Complete outstanding reference-feature semantic coverage and external runtime/component advisory review.
4. Extend memory and Forge incrementally: preserve privacy and deletion boundaries; design a separately secured executable-skill runtime before generating executable candidates. Available-runtime probes found no qualified Docker/Podman or installed WSL environment; fixed declarative workers do not fill that gap. Activation must remain owner-approved.
5. Implement and qualify opt-in local microphone/STT/playback/interruption, then test English/Hindi where supported. Personal "Hey SIGHT" enrollment awaits owner recordings and explicit consent. Add selected-window/input/file-organization and authorized remote-browser adapters only with scoped targets, previews, deadlines and audit records.
6. Build planning, controlled concurrency and independent verification on the existing durable jobs, and add disposable-worktree repair validation before offering any generated code change for promotion. Keep these experiments separate from release readiness.

The current evidence closes the bounded current-build one-hour stability gate and supports the repaired local scope above. It does not resolve the installation/browser limitation, certify the entire reference feature set or establish the requested broader roadmap as production-ready. **Final verdict remains PARTIAL; no release or push is authorized by this report.**
